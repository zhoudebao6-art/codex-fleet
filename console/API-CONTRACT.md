# Fleet Site API contract

All responses are JSON except file bodies. Errors: `{error, code?}`. Browser mutations require the exact same Origin and JSON content-type (file PUT uses application/octet-stream). Browser access prefers a local username/password session, then an authorized platform ChatGPT identity, then a valid device session. Every session checks current admin/operator/viewer membership or device project permissions. Devices use their independent Fleet bearer token plus the separate private-Sites platform header when that hosting boundary is enabled; no platform token appears in API responses.

- `GET /health` → `{ok,version,protocol:1}` (still subject to private Sites access).
- `GET /api/console/me` → `{user:{id,email,name,role}|null}`.
- `POST /api/console/login {username,password,remember?}` → `{ok:true,user}` and HttpOnly/Secure/SameSite cookie; local users have `{id,username,name,email:null,role,kind:"local"}`. Ordinary sessions last 12 hours; remember lasts 30 days. Usernames are normalized lowercase, 2–64 letters/digits/._-; new passwords contain 6–512 characters. Generic failure messages and per-user/per-IP throttling apply.
- `POST /api/console/logout {}` revokes the current local/device cookies and server sessions.
- `POST /api/console/password {currentPassword,newPassword}` changes the signed-in local user's password, revokes all that account's sessions, and returns `{ok:true,reauthenticate:true}`.
- Admin `GET /api/console/accounts` → `{accounts:[{id,username,role,active,created}]}`; `POST {username,password,role}` creates an account; `PATCH /accounts/:id {role?,active?}` changes role or disables access; `POST /accounts/:id/password {newPassword}` resets password and revokes sessions. The last active administrator cannot be disabled/demoted. Local accounts must be managed here, not through the optional ChatGPT members endpoint.
- Admin `GET /api/console/backup` downloads a versioned `partial_metadata_backup` JSON. It excludes password hashes/salts, credentials, sessions, invitations, and R2 file bytes. It is explicitly not a complete restorable backup; file entities need separate download.
- `GET /api/console/installer` returns a real registered `{version,name,size,sha256,project,downloadUrl}` or `null`; unauthorized project viewers also receive null. Admin `POST {version,name,sha,size,project}` requires a matching completed ZIP file and registers it. The download URL uses the authenticated file route, never a fabricated public link.
- `GET /api/console/overview?after=0&limit=100` → `{nodes,tasks,events,files,cursor}`. `?tail=100` returns the latest N events in ascending seq order (0–500); use the last seq as `after` for incremental polling. Events have seq,nodeName,taskName,sourceId,sourceName,targetNode,targetName,payload,created. Message event payload includes authorized message text,sender,sourceName,targetNode,targetName. Device rows have id,name,projects,lastSeen,online,revoked,capabilities,accountGroup.
- `GET /api/console/members` → `{members:[{id,email,role,userId,created}]}`; admin `POST {email,role}`, `PATCH /members/:id {role}`, `DELETE /members/:id`. No automatic first-visitor ownership; only configured owner email bootstraps.
- `POST /api/console/invites {name,projects:["workspace"],accountGroup?,hours?}` → `{hubUrl,token,name,projects,expires,id}`. One use, repeat enrollment for the same device/token is idempotent. Invitation has no platform access credential.
- `GET /v1/nodes` → node array. Admin `POST /v1/nodes/:id/revoke`.
- `GET /v1/tasks` → latest task array (up to 500), optional target/status/limit, retained for old clients. `GET /v1/tasks/page?target=&status=&q=&limit=50&cursor=` → `{tasks,nextCursor,total,serverTime}` covers the complete authorized task directory. Limit is 1–100; search matches task ID, project and prompt with literal SQL wildcard characters. Stable created/id keyset cursors are tied to the filter and caller project scope; reset the cursor when changing filters. `POST /v1/tasks` accepts `{id,targetNode,project,prompt,skills:[],outputs:[],dependencies:[],inputs:[{sha,size,name}],role?,acceptance?,parentId?,resumeTaskId?,worktree?,baseCommit?,model?,workspaceId?,executionPolicy?}`. Input files must already be complete in the same project. Task has id,creator,target,project,status,spec,result,thread_id,attempt,created,updated. Existing identical id returns the original task.
- `GET /v1/tasks/:id` → task plus artifacts and inputs arrays. `GET /v1/tasks/:id/events`, `/messages` → arrays. Events support `?tail=100` for initial latest progress, then `?after=<lastSeq>&limit=500`; after pagination retains ascending sequence and never skips intermediate events. `POST /messages {id?,text}` → message. `POST /accept {note}`, `/cancel {}`, admin `/resolve {confirmStopped:true,note}`.
- `POST /v1/enroll {token,nodeId,nodeToken}` → `{nodeId,name,projects,accountGroup,groupSalt}`.
- Node-authenticated `POST /v1/device-session {}` → `{ticket,expires,siteUrl}` (60 seconds, one use). Browser same-origin `POST /api/console/device-session {ticket}` consumes it, sets a HttpOnly/Secure/SameSite cookie, and returns `{ok:true,user}`. The 7-day device session is scoped to the live node's projects and is revoked with that node; it cannot manage members or invitations. An authorized ChatGPT member identity takes precedence over a device cookie.
- `POST /v1/sync {events,capabilities}` → `{ack,tasks,serverTime,protocol:1,nextPollMs}`. Events retain old assign/message/started/progress/uncertain/finished forms. `progress` may include input receipt fields; no receipt is automatically treated as file read.
- `POST /api/console/files {id,sha,size,name,project}` → `{offset,complete,chunkSize:8388608}`. `PUT /api/console/files/:sha?project=workspace&offset=0` sends binary chunks, max/recommended 8 MiB; legacy 1 MiB is accepted. Response `{offset,complete,chunkSize:8388608}`. GET same path streams complete file. File sizes ≤512 MiB; size zero completes at initialization. Same content is scoped to project; final full SHA256 is checked while streaming persisted chunks.
- Devices use the identical upload/download contract at `/v1/files` and `/v1/files/:sha` with their node bearer token. They do not call `/api/console/files`. After upload, use the resulting sha/size/name in a normal task's inputs.
- Administrator `POST /api/console/files/:sha/reset {project,reason}` explicitly resets a corrupt or abandoned incomplete upload, returning `{ok:true,generation,offset:0,complete:false,chunkSize:8388608}`. Completed files and files referenced by queued/claimed/running/uncertain/cancel_requested tasks cannot be reset. The next authorized initialization claims the new upload and can correct declared size/name. Reset increments the storage generation atomically, clears old D1 chunk references, records an audit event, and prevents in-flight old PUT/digest operations from mutating the new generation. Old R2 objects are retained in isolated generations for separate bounded maintenance; this operation does not delete completed user files. Stop the sender with wrong source bytes before resetting, then initialize again with the corrected source.
- `GET /v1/artifacts/:sha?task=:id` supports Range and serves both declared task inputs and completed outputs. Execution node output `POST {size,name}`, `PUT ?offset=`, `HEAD` retain v0.1.1 upload semantics.
- `GET /v1/knowledge?project=&q=`, `POST /v1/knowledge {project,key,body,sourceTask}` retain accepted-source rules.

Task state: queued → claimed → running → submitted/failed/blocked/cancelled; cancellation may be cancel_requested until target confirms. Crashed attempts become uncertain and are never reassigned by a heartbeat timeout. `submitted` still needs explicit acceptance.

Overview additionally returns `taskStats:{total,byStatus:{status:count},byNode:[{nodeId,total,byStatus}]}`. These are full database aggregates within the caller's authorized project scope, independent of the recent tasks/events page size. A missing status key means zero. Use these counts for home and device summaries; the `tasks` array remains a recent slice and must not be treated as the complete set.

Overview `runningProjects` is an array of `{id,nodeId,nodeName,project,name,workspaceId,root,total,fleetCount,desktopCount,currentTasks,latestActivity,latestActivityAt}`. Groups cover the full authorized active set, keyed by computer, project scope and normalized actual directory; bound Fleet worktrees belong to their registered workspace. Each group keeps up to eight recent `currentTasks` references while counts remain complete. A reference is `{kind:"fleet"|"desktop",id,nodeId,threadId?,taskId?,title,status,phase,evidence,updatedAt,cwd,workspaceId}`. Fleet phases are preparing/running/uploading/waiting/cancel_requested, based on a fresh node heartbeat and matching `capabilities.taskRuntime:{taskId,attemptId,phase,cwd}[]`, legacy active-task evidence or a recent actual upload event. A stored running task row alone is not confirmation. Desktop records require unarchived running state from `app_server_runtime`, fresh observation and receipt within two minutes, and an online node heartbeat within one minute; recent activity, persisted old turns and offline records are excluded. A native thread already represented by an active Fleet task is counted once. Unknown directories remain null and must not be presented as an exact named project.

Project history uses `workspaceId`, `cwd` (alias `root`), `project` and `phase=all|active|completed` on `/v1/tasks/page` and `/v1/desktop/threads`. A workspace ID is validated against project scope and resolves its real directory plus bound worktree sessions. A raw cwd requires `target` for Fleet tasks or `nodeId` for desktop threads; comparisons normalize Windows case, separators and trailing separators and do not match similarly named sibling folders. Cursor identity includes these filters. Fleet completed means submitted/accepted; desktop completed means completed and includes archived records unless `archived=false` is requested. The desktop active filter requires fresh confirmed running/waiting runtime evidence. Fleet active includes claimed/running/cancel_requested/uncertain states, each retaining its actual status label. Fleet page rows and task detail include `completedAt` from the matching node and attempt's submitted finish event, never from a later acceptance/update time; absence of reliable completion evidence yields null.

File input metadata uses sha (not sha256). Browser uploads first, then sends task inputs. The Windows adapter downloads and verifies inputs before starting Codex in the actual task directory, and emits progress receipts. Web file records expose id,sha,size,name,project,status,offset,created,updated without R2 keys or credentials.

## Desktop Codex directory

- Node `POST /v1/desktop/sync {threads:[...],inventory?,snapshotAt?}` accepts at most 20 rows and 1 MiB per request. Identity is bound to the authenticated node. All rows are validated before one atomic D1 batch. Replaying a batch is safe; older `observedAt` does not replace a newer row. Omitted records are retained, including archived sessions. It returns `{ok:true,ack:[threadId],readRequests:[threadId],serverTime}`.
- A row contains `threadId,project,title` (240 chars), `preview` (1,000), `cwd` (2,000), `archived,source,createdAt?,updatedAt,observedAt,status,statusSource,lastActivityAt?,activeFlags?,parentThreadId?,fleetTaskId?`. Project must be authorized for that node. `fleetTaskId`, if supplied, must name a task assigned to that node in that project and with the same thread ID when known. Same-account devices still have independent `(node,threadId)` keys.
- Status is `unknown|running|waiting|failed|completed|interrupted|recent_activity`; status source is `stored_metadata|app_server_runtime|persisted_turn|recent_public_activity`. Stored activity is not proof of a currently running desktop turn.
- When details were actually reread, send `detailUpdatedAt` with `latestUserMessage/latestAssistantMessage` (4,000 chars each) and up to 30 public `activities`. Activity types are `user_message|assistant_message` with `{id,turnId?,at?,text}`, or `tool_activity` with `{id,turnId?,at?,toolType,tool,status,exitCode?}`. Hidden reasoning, raw command arguments, tool outputs and arbitrary fields are not stored. A metadata-only update preserves prior details. Changing the authorized project clears retained details until they are supplied for the new project.
- Inventory is `{scannedAt,complete,count,error?,detailErrors?:[{threadId,error}]}`. It describes the local scan, not completion of every cloud upload. Compare returned `storedCount` with `count` before claiming directory synchronization is complete. Errors are bounded; partial scans never delete earlier rows.
- `GET /v1/desktop/threads?nodeId=&q=&archived=all|true|false&pinned=true|false&limit=30&cursor=` returns `{threads,nextCursor,total,inventories,serverTime}`. Limit is 1–100. Cursors are bound to the filter and project scope. Rows include `nodeId,nodeName,threadId,...metadata,pinned,pinnedBy,pinnedAt,receivedAt,detailUpdatedAt,detailReceivedAt,freshness,statusFreshness,nodeOnline`; `workspace` aliases `cwd`, and `recentActivityAt` aliases `lastActivityAt`. Freshness values are `fresh|stale|unknown`. Lists intentionally omit message bodies.
- `GET /v1/desktop/summary` returns `{nodes:[{nodeId,nodeName,inventory,threads,latestThread}],serverTime}`. Each node has three rows ordered by pin then modification time; `latestThread` independently identifies its most recently changed task.
- `GET /v1/desktop/threads/:nodeId/:threadId` returns one authorized row plus `latestUserMessage,latestAssistantMessage,activities,messages,inventory,detailPending,detailState,refreshRequested`. Missing or stale detail schedules a read-only refresh on the owning device. The website may poll every five seconds while open. `POST .../refresh {}` explicitly requests rereading. A new detail observation clears the request using server receipt time, so ordinary differences in PC clocks do not leave the request stuck. Old detail replays do not satisfy a later refresh.
- Operator/device `POST` or `PATCH .../pin {pinned:boolean}` marks a shared principal task. Readers can see pins; viewers cannot change them. No endpoint resumes or modifies the underlying desktop Codex session.

## Human interactions and node maintenance

- Execution node `POST /v1/tasks/:taskId/interactions {id,attemptId,kind,method,request,expiresAt}` creates an idempotent interaction tied to the current task attempt. Allowed kinds are `elicitation|questions|approval`. Lifetime is at most 24 hours. `GET` on the collection returns `{interactions,serverTime}`; each interaction contains `id,taskId,nodeId,attemptId,kind,method,request,status,expiresAt,createdAt,response,answeredBy,answeredAt,resolvedAt`.
- Display request fields are allowlisted: `message,command,reason,cwd,display,serverName,mode,url,availableDecisions,requestedSchema,questions`. URLs must use HTTPS and cannot contain username/password components. Arbitrary request data is not published. Schema objects support bounded basic types, nested properties/arrays, enums and bounds. Unknown constraints are marked unsupported and cannot be silently accepted remotely.
- A signed-in browser operator or administrator responds with `POST .../:interactionId/respond {response:...}`. Node bearer credentials and the maintenance token cannot impersonate a human responder. Elicitation accepts `{action:"accept",content:{...}}`, `{action:"decline"}` or `{action:"cancel"}`. URL-mode elicitation accepts an explicit human `{action:"accept"}` without form content. Questions use `{answers:{questionId:{answers:["text"]}}}`; empty arrays represent skipped questions. Approval uses `{decision:"accept"|"decline"|"cancel"}` for a single command/file request only. Requests to change permission policy or grant broader permissions remain local.
- An identical human answer is idempotent; a different later answer conflicts. Expired, cancelled, completed or replaced attempts do not accept new answers and do not expose an unapplied answer to the execution node. Node `POST .../:interactionId/resolve {attemptId}` records that an existing human answer was sent to local Codex. The same execution node and attempt may acknowledge an answered, unexpired request after the task completes, so a fast turn cannot lose its delivery receipt. This does not mean the requested action or task has completed. Every phase emits an audit event containing IDs/kind, not response content. Answering never changes a task's execution mode or sandbox.
- Node `POST /v1/node/maintenance {enabled,reason?,expiresAt?}` pauses new claims only for that authenticated node. Default lifetime is 15 minutes, maximum one hour; `enabled:false` clears it. Existing tasks, events and files continue draining. Claims check the maintenance row atomically, including for legacy adapters. Node listings include `maintenance:{enabled,expiresAt,reason}`; expiry automatically releases the pause.

## Project workspaces

- `GET /v1/workspaces?nodeId=` returns `{workspaces,discovered,discoveredHasMore,serverTime}`. Registered rows have `{id,nodeId,nodeName,project,name,root,path,source,sourceThreadId,controllerThreadId,automationNote,status,error,createdAt,updatedAt}`. Status is `pending|ready|error`; source is `created|discovered`. The `project` value remains the existing authorization scope, separate from the actual filesystem directory. Discovery groups observed desktop task directories by device/project and normalized Windows path; at most 1,000 groups are returned with an explicit overflow flag.
- Operator browser or authorized node controller `POST /v1/workspaces {id?,nodeId,name,project?,automationNote?,sourceThreadId?}` registers a project. The caller and target must both have the project scope; node credentials cannot create projects in unrelated scopes. Use a stable `id` for safe retry. Omit `sourceThreadId` for a new project; its root starts null and the node creates it under its configured project root's `projects/<id>` directory. For an existing project, supply an actual observed desktop thread; the server derives the directory from that record. Client-specified `root/path` are rejected. Re-registering the same directory returns its existing workspace.
- Target node `POST /v1/workspaces/:id/ack {status:"ready",root}` confirms the actual directory or `{status:"error",error}` reports failure. Only that node can acknowledge; the registered directory is immutable. A failed directory check can subsequently recover to ready. No existing files are overwritten merely by registration.
- Operator `PATCH /v1/workspaces/:id {name?,automationNote?,controllerThreadId?}` updates coordination metadata. A controller must be an observed desktop thread on the same device in the same project directory; null unbinds it. `GET /v1/workspaces/:id/threads` returns `{threads,controllerThreadId}` with up to 100 recent candidates. The controller binding is context for coordination, not permission to take over a running desktop thread.
- Normal task specs may add `workspaceId`. Submission validates the ready workspace, target device and project scope. The target must advertise `capabilities.workspaceExecution:true`; otherwise it cannot claim such a task. This prevents older adapters from ignoring the new field and working in the wrong directory. Continuations must keep the same workspace as the preceding task. Existing task specs without a workspace ID retain their previous behavior.

## Sequential unattended automations

- Operator/member, device browser or project-scoped node controller `POST /v1/automations {id,name,project,steps:[{key?,name,targetNode,workspaceId?,prompt,mode?,executionPolicy?,skills?,outputs?,worktree?}]}` creates and starts a durable flow of 2–12 sequential steps. Use a stable flow `id` when retrying. Every target, workspace and output path is validated before storage. A changed declaration with the same ID returns conflict. Each step has its own deterministic task ID and immutable prepared task spec.
- `GET /v1/automations?status=&limit=100` returns `{automations,hasMore,serverTime}` (limit 1–200). `GET /v1/automations/:id` returns one flow. Flow fields are `id,name,creator,canManage,project,status,currentStep,totalSteps,error,createdAt,updatedAt,lastCheckedAt,completedAt,steps,result`. `canManage` is computed for the requesting actor (creator with write permission, or administrator). `currentStep` and each step's `index` start at zero. Steps retain their declared fields plus `taskId,status,summary,updatedAt`. Planned/prepared steps have no executing task; otherwise status is the actual task state. Results become available when the final step completes, including its summary and complete output-file references.
- Flow status is `running|paused|needs_attention|completed|cancelling|cancelled`. Creator or administrator `POST /:id/pause {}` prevents new claims while allowing the current attempt to finish. `POST /:id/resume {}` resumes eligible paused work; it does not repeat a failed, blocked or uncertain step. `POST /:id/cancel {}` cancels queued work and requests active attempts to stop; the flow remains cancelling until the worker confirms termination. These controls are enforced in the same SQL write as task claims, including creator revocation checks.
- A node heartbeat drives at most ten flows, with least-recently-checked rotation. No separate cron or additional server is required. A completed step must have task status `submitted` or `accepted`, with exactly one complete artifact for every declared output. Its bounded result summary and checked file references become the next task's prompt context and inputs, preserving original relative file names. Repeated names or file/parent path conflicts reject. Missing or ambiguous outputs stop the flow with an explicit error.
- Prepared successor task specs are stored before submission and reused after concurrent ticks, process interruption or lost acknowledgements. Reserved automation task IDs cannot be claimed by independent manual submissions. Existing worker retry and recovery behavior remains responsible for a task attempt; automation never silently repeats a potentially side-effectful failed attempt.
- `submitted` remains execution completion, not business acceptance. Automatic handoff does not change it to `accepted`. Add a separate review step and a final summarization step when the workflow requires those outcomes. Human input is needed only when an actual interaction, failure, uncertain execution or other declared exception prevents progress.
- Task and step `executionPolicy` is `local|project`. `local` requires explicit execute mode and `capabilities.localExecutionPolicy:true`; legacy adapters cannot accept or claim it. It tells the adapter to use the target computer's existing Codex execution policy, without changing global settings. Automation execute steps default to local; question steps default to project/read-only and cannot select local. Ordinary legacy task specs that omit this field keep their previous behavior.

## Device names, organization and upgrades

- Nodes retain stable `id` and `name` (also exposed as `code`) for authentication and existing tool addressing. Listings add `displayName` (friendly name or code), `groupId` and `groupName`. Administrator `PATCH /v1/nodes/:id {displayName?,groupId?}` changes only these website organization fields; null resets either value. Names can contain Chinese text and are limited to 120 characters. Device capabilities and heartbeats cannot overwrite them. This route cannot change project authorization, credentials, account-group concurrency or the stable code.
- `GET /v1/device-groups` returns `{groups:[{id,name,sortOrder,nodeCount,createdAt,updatedAt}]}`. Scope-limited readers see only groups containing authorized computers and scoped member counts. Administrator `POST {id?,name,sortOrder?}`, `PATCH /:id {name?,sortOrder?}` and `DELETE /:id` manage display groups. Group names are 1–80 characters. Deleting a group atomically clears existing devices and pending invitations to ungrouped, without revoking devices or changing permissions.
- Invitations accept optional `displayName` and `groupId`, and enrollment initializes these fields. The invitation `name` remains the stable computer code. Repeating enrollment never overwrites organization changes made after initial enrollment.
- Administrator `POST /v1/nodes/:id/upgrade {id?}` creates one persistent upgrade action. Use a stable action ID for retries. It requires `capabilities.selfUpgrade:true`; older adapters return `NODE_UPGRADE_BOOTSTRAP_REQUIRED` instead of pretending to support automatic upgrade. The server snapshots only its currently registered installer with matching completed file name, SHA256, size, version and authorized project. The body cannot supply commands, paths, URLs or a different installer. Each node can have at most one active action.
- Node-only `GET /v1/node/actions` returns `{actions,serverTime}` for that node's active actions; administrator `GET /v1/nodes/:id/actions` returns the latest 20 records including terminal results. Action fields are `{id,nodeId,action:"upgrade",status,installer:{sha256,size,version,name,project},downloadPath,bytes,detail,version,packageSha256,createdAt,updatedAt}`. `downloadPath` is always the same hub's `/v1/files/:sha?project=` route, using the immutable installer snapshot.
- The target node acknowledges with `POST /v1/node/actions/:id/ack {status,bytes?,detail?,version?,packageSha256?}`. States are queued → downloading → waiting → installing → completed/failed. Waiting means the verified package is queued locally while existing work drains. Bytes never decrease; old intermediate acknowledgements cannot regress state. Waiting/installing/completed require the selected SHA256; completed additionally requires the selected installed version. A matching package/version completion acknowledgement may recover after interruption even if an intermediate acknowledgement was lost. Terminal acknowledgements are idempotent only when repeated unchanged. A deliberate new administrator action is required after failure.

## Browser group access and native continuation (0.3.3)

`access` is `{mode:'all'|'groups',groupIds:string[]}`. `__ungrouped__` is the explicit ungrouped-device grant. `all` requires an empty groupIds list. Administrative identities always have all access. New non-admin members/local accounts and new device browser permissions default to an empty group list. Migration 0009 explicitly retains all access for existing members and devices; token hashes, sessions, device identities, project authorization and account concurrency groups are preserved.

- Accounts: GET/POST/PATCH `/api/console/accounts` and `/:id` expose/accept access. DELETE `/:id` removes the member/account and all login sessions. Last active administrator protection applies to role changes, disabling and deletion.
- Platform members: GET/POST/PATCH `/api/console/members` and `/:id` expose/accept access. DELETE prevents implicit owner auto-bootstrap from resurrecting the removed membership. Explicit administrator recreation is permitted.
- `/api/console/me` user includes access and memberId where relevant. Existing id semantics are retained: a platform userId where supplied, otherwise member:id.
- Admin PATCH `/v1/nodes/:id` additionally accepts `consoleRole:'operator'|'viewer'` and `consoleAccess:access`. These only govern the passwordless browser identity. Normal node bearer credentials retain their original project collaboration permissions. Admin node lists expose the console fields.
- Group deletion unassigns nodes and invitations, removes that group from explicit user/device browser grants, and deletes standalone file grants for the group. It never substitutes ungrouped or all access. Reusing a deleted group ID does not resurrect old grants.

The server applies browser group scope before task/event/file/project/desktop/flow pagination or aggregation, including overview totals and running projects. Direct detail, messaging, interactions, task inputs/dependencies/continuations and project binding paths enforce the same scope. A workflow is visible only if all declared target devices are visible. Roles and group permissions are re-read each browser request. Pending browser tasks and workflow steps recheck current role/group grants in the atomic claim SQL. Workflow advancement rechecks the creator across all targets; revoked access stops progression with needs_attention. Previously recorded node-owned workflows remain node-owned; new workflows created through a passwordless browser use a separate device creator identity.

Standalone browser uploads by restricted users require `groupId` on POST `/v1/files` or `/api/console/files`; when exactly one group is authorized it is inferred. Multiple groups without a selection return 403 `UPLOAD_GROUP_REQUIRED`. Admin/all browser callers may also provide a valid groupId. Standalone file grants are persisted independently of the uploader, and withdrawal removes access even for that uploader. Files are readable only through a permitted device owner, permitted task reference, or explicit permitted file-group grant. Unscoped historical admin/browser uploads are not exposed to restricted users merely by knowing the content hash. Normal node uploads are unchanged.

POST `/v1/desktop/threads/:nodeId/:threadId/message` accepts exactly `{id,prompt}`. It requires a writing identity, desktop/project/group access, an unarchived synchronized thread, a fresh online node heartbeat and `capabilities.desktopContinuation===true`. It constructs the task from the synchronized target/project/cwd/thread ID, fixes mode=execute and worktree=false, and does not override model, sandbox, approval, or execution policy. Generic POST tasks rejects desktopThreadId/desktopCwd. Exact stable-id retries return the existing task, including when the node subsequently goes offline; changing the prompt under the same ID rejects.

The insertion atomically allows only one queued/active continuation of the same node/thread, considering native references, actual task thread IDs and prior Fleet resume references. A result.desktop.state=uncertain retains this lock even when the task is blocked or cancelled; only the existing administrator resolve action with confirmStopped=true and an evidence note clears it. Claims require the native capability to remain advertised. Node execution must independently validate the real local directory and acquire Codex's official writer lock. Occupied original conversations report a terminal blocked task with result.desktop.state=busy; they are not stolen or automatically retried. HTTP 409 codes are NODE_OFFLINE, NATIVE_CONTINUATION_UNSUPPORTED, NATIVE_THREAD_ARCHIVED, NATIVE_DIRECTORY_UNAVAILABLE, NATIVE_CONTINUATION_PENDING and NATIVE_CONTINUATION_REQUIRED.

Desktop details expose fleetTaskId/fleetTaskStatus/fleetTaskNative only for matching target/project and the actual task thread_id or trusted desktopThreadId. Unresolved requests take precedence. Ordinary Fleet conversations retain their existing continuation flow; native-origin tasks and threads already continued through the native route reject generic resumeTaskId with NATIVE_CONTINUATION_REQUIRED. Their follow-ups must use the dedicated native message endpoint, including after successful completion.

Device runtime and recovery

- Node lists expose effective `runtime`: heartbeat age, executor connection, maintenance and desktop checks determine readiness. `/v1/nodes/:id/capacity` exposes device and shared-account reservations. Ordinary tasks, native conversations and fresh observed native turns share the same atomic claim budget; a continuation into an existing thread reuses its slot. Existing attempts are never cancelled when capacity is lowered.
- Administrator GET `/v1/delivery/controller-recovery` returns a revision, blockers and eligible replacement controllers. POST requires `{id,target,revision,reason}`. Transfer rejects online controllers, active or uncertain related work, unfinished skill workflows, stale revisions and unsuitable replacements. It preserves task/attempt IDs and pauses unfinished active batches. Normal settings updates cannot bypass this path.
- Controller ticks and acknowledgements hold a short database lease. Every mutation checks the lease and current controller inside its D1 transaction; expired handlers cannot write after a replacement. Recovery temporarily excludes new claims while ownership changes.
- Administrator POST `/api/console/backups` with a stable `{id}` creates an immutable transactional business snapshot. GET lists snapshots; GET `/api/console/backups/:id/download` streams NDJSON with stored file bytes, chunk checksums and a final archive digest. Missing content fails the stream without a success footer. `verifiedAt` means source bytes were read and checked, not that a user restored them.
- `/fleet-restore.mjs` restores into a new isolated directory using Node 22 or newer. It verifies all rows and file contents, disables identities and pauses execution. Credentials, unsynced local files and Codex's own conversation database are excluded. Its `local-store` command separately creates a consistent SQLite copy including committed WAL data without stopping the original node.
- Backup views expose stable `segments` capped around 64 MiB of serialized content. `download?part=N` streams one independently checksummed segment. All segments must be downloaded before the server marks the backup verified. Large backups can be saved sequentially to a chosen browser directory, or downloaded individually; restore starts from segment 1 and checks every segment, schema, record count and file digest. Small R2 reads are coalesced into 256 KiB records to bound encoding overhead.
